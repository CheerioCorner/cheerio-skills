# Travel Map Page Content

根據標的物類型，產出一份**查證過、能實際帶去用的紀錄**，不是套模板腦補。

## ⚠️ 核心理念

**不是套模板，而是針對這個地方查證後產出報告。**

跟 `knowledge-garden-page-content` 同一個精神，但風險更具體：地址寫錯、簽證流程寫錯、營業時間寫錯，使用者是真的會帶著這份資料出國、走進一間可能已經關掉的店。**沒有查證來源的事實類資訊，寧可標記「未查證」，也不要用肯定語氣寫錯的東西。**

**不要只讀 Properties 就產內容。** 必須先查證。

**本 skill 目錄下的資產**（開工前知道有這些就好，不用先讀過一遍）：
- `assets/templates/地方誌-content.md`、`assets/templates/見聞錄-content.md` — 頁面正文的骨架，Phase 1 會指定用哪一份
- `references/dining-profile.md` — **同行者飲食限制檔案。處理任何餐廳前必讀**，不是選讀
- `references/notion-markdown-syntax.md` — 需要分欄/callout 等排版時查

---

## 適用範圍與骨架

沿用 `travel-map-query` skill 的 `schemas/travel_map_schema.yaml` 裡 `page_content_templates` 定義的三段式，本 skill 負責把「蒐集資料」段落寫紮實：

| 資料庫 | 段落 | 本 skill 負責程度 |
|--------|------|------|
| 地方誌 | 📖 蒐集資料（未驗證） | ✅ 查證後寫入 |
| 地方誌 | 🚗 自駕實務 | ✅ **強制 Enriched ＋ 官方來源**，比照簽證 |
| 地方誌 | 🗣️ 語言功課 | ✅ 主要負責——句型要附中文近似音，能直接唸 |
| 地方誌 | 🎫 票券與套票 | ✅ 列選項與規則；**不下「哪張划算」的結論**（那是 route 拿實際行程去算） |
| 地方誌 | 🏛️ 歷史脈絡速讀 | ✅ 主要負責，歐洲條目必寫 |
| 地方誌 | 🗓️ 什麼時候去 | ✅ 查證後寫入 |
| 地方誌 | 🛍️ 想帶回家 | ✅ 寫選項；實際戰利品由 `travel-map-trip-feedback` 累加 |
| 地方誌 | 💡 想做的事 | ⚠️ 只整理使用者口述的想法，不代為發想 |
| 地方誌 | ✅ 親身驗證心得 | ❌ 不負責——由 `travel-map-trip-feedback` 寫入 |
| 見聞錄 | 📖 蒐集資料（未驗證） | ✅ 查證後寫入，**含座標與當地語言名稱** |
| 見聞錄 | ⭐ 評論重點 | ✅ 主要負責——歸納不是照抄，見 Phase 0 |
| 見聞錄 | 🍽️ 飲食適配（餐廳） | ✅ 主要負責，依 `references/dining-profile.md` 逐條判定 |
| 見聞錄 | 🗣️ 點餐與菜單關鍵字（餐廳） | ✅ 主要負責 |
| 見聞錄 | 🏛️ 背景故事／看點（景點） | ✅ 主要負責 |
| 見聞錄 | 🎫 購票怎麼開口（景點） | ✅ 主要負責 |
| 見聞錄 | ✅ 親身驗證心得 | ❌ 同上，不代為捏造 |

### 本 skill 可以回填的屬性

查證的產物直接寫回，不用繞回 `travel-map-knowledge-capture`（schema `write_ownership` 已載明）：

`外部評分`、`評論數`、`評價查證日`、`座標`、`當地語言名稱`、`建議停留`、`飲食適配`、`子類別`、`來源連結`、`AI 摘要`、`最後更新`

**不要**碰：`成熟度`（feedback 專屬）、`喜愛度`（feedback 專屬）、`所屬地方誌`／`類別`（capture 專屬）。

## Mode 切換

| 條件 | 模式 | 說明 |
|------|------|------|
| 只有店名/景點名，沒有網址、沒有城市脈絡 | Quick Draft | 用 WebSearch 查基本資訊（地址、營業時間、類型），查不到就只留使用者提供的資訊 |
| 使用者給了網址、Google Maps 連結、或明確要求「查一下」「深入」 | Enriched | 完整查證流程 |
| 內容屬於簽證/入境規定/法規類 | **強制 Enriched**，且必須找官方或高權威來源 | 這類資訊寫錯有實際後果（可能被拒絕入境、罰款），不接受「憑印象寫」 |
| 內容屬於**自駕規則**（ZTL/環保區/vignette/限速/停車） | **強制 Enriched ＋ 官方來源** | 同上，寫錯是直接吃罰單 |
| 標的是**餐廳** | **強制查菜單** | 沒看到菜單就無法判定飲食適配，一律填 `❓ 待確認菜單`，不要用菜系推測 |

**Quick Draft 不等於腦補。** 即使跳過完整查證，只要查得到來源就要標註；查不到就明確寫「未查證，待確認」，並在成熟度旁的內容裡留一句提醒，不能寫得像已經查證過。

## Phase 0：查證

### 見聞錄（餐廳/景點/住宿/店家）

1. 有網址（官網/Google Maps 分享連結/食記）→ WebFetch 抓取
2. 沒有網址 → WebSearch `<店名/景點名> <所屬地方誌的城市或區域>`，找官方頁面或近期評論
3. 都查不到 → 只留使用者原始描述，內容標註「⚠️ 未查證來源，資訊由使用者提供」

**每一筆見聞錄都要抓齊這幾樣**（不是有空才抓）：

| 要抓的東西 | 為什麼 |
|-----------|--------|
| 地址 ＋ **座標**（緯度,經度） | 沒座標就排不了動線、匯不出地圖。Google Maps 網址裡的 `@lat,lng` 直接就有 |
| **當地語言名稱**（原文） | 非英語系國家的關鍵——搜尋、給司機看、現場對招牌都靠它 |
| 營業時間（含公休、最後入場/點餐） | 動線衝突檢查要用 |
| **外部評分 ＋ 評論則數** | Cheer 篩品質的主要依據。只給星等不給則數等於沒給 |
| 建議停留（分鐘） | 查不到就依類型估：餐廳 90／博物館 120／教堂 40／觀景點 30，並註明是估的 |

### 評論歸納（見聞錄必做）

**不要照抄評論，要歸納共識。** 這是本 skill 對 Cheer 最有價值的產出——他原本要自己讀幾百則。

1. 抓一批近期評論（優先看最近 12 個月，舊評論的資訊常常過期）
2. 產出固定三行：**好評共識**（多數人反覆提到的優點）／**負評共識**（多數負評的共同點）／**踩雷風險**（什麼情況會失望：排隊、只收現金、需預約、觀光客價、換老闆）
3. 星等一定要跟則數一起寫。4.9 但 12 則跟 4.3 但 8000 則，是兩回事，要在文字裡點出來

### 餐廳的飲食適配（強制）

1. **先讀 `references/dining-profile.md`**，不要憑記憶
2. 找菜單（官網、Google Maps 相片裡的菜單、外送平台頁面、食記裡的菜單照）
3. 逐條判定非牛主餐／素食主餐（原型還是加工素肉）／口味鹹度，**每一條要指出依據**
4. 找不到菜單 → 三條全寫「待確認」，`飲食適配` 屬性填 `❓ 待確認菜單`。**不要用菜系推測**（「日式一定有魚」「印度菜一定有素」都是猜）
5. 「✅ 全家皆可」是結論，門檻見 dining-profile，不要寬鬆給

### 語言功課（地方誌必做；見聞錄視類別）

Cheer 的主要溝通語言是英文而且自評不好，去的又常是非英語系國家，所以語言功課是**出發前在台灣做完、到當地離線用**的實戰卡片。

1. 先確認地方誌的 `英文通用度`；🟠/🔴 的地方，語言功課與當地語言名稱是必備不是加分
2. 每一句都要三行：**當地語原文 ＋ 羅馬拼音 ＋ 中文近似音**。近似音要能直接唸出來（用中文字寫），不要用 IPA
3. 一定要有那句**免責開場**：「我只會一點點，我們可以講英文嗎？」——Cheer 習慣先講這句再切英文
4. 一定要有**指著就能用的短句卡**：「我不吃牛」「我吃素，不要肉和魚」「請不要太鹹」的原文，讓他不方便開口時直接把手機遞過去
5. 拼音與唸法查不到可靠來源就標「近似音待確認」，不要自己音譯亂編

### 地方誌（國家/城市/區域級知識：簽證、交通通則、習俗）

1. **簽證/入境規定**：優先查該國官方外交部/移民署網站，或台灣外交部領事事務局；次要來源是知名旅遊媒體的近期文章（需標明發布日期，規定常變動）
2. **交通通則**（JR Pass、Grab、當地地鐵）：官方交通局網站或近期實用攻略
3. **自駕規則**（ZTL、低排放區、vignette、限速、停車、加油、收費道路）：**比照簽證，強制官方來源**。優先查該國交通主管機關、租車公司官方說明、當地市政府的管制區公告。潛規則（當地人怎麼開）可以用近期駕駛經驗分享補充，但要標明來源性質。
4. **票券與套票**：查官方售票網站，把票種/涵蓋/效期/價格/購買通路/是否需預約時段列成表。**不要在這裡判斷哪張划算**——那要拿實際行程去算。
5. **習俗**：泛用旅遊資訊來源即可，風險較低，可以稍微寬鬆
6. **歷史脈絡**：博物館/官方觀光局/百科等級的來源即可；重點是寫成「走在街上看得到什麼」，不是年表複述
7. 查證後的每一項事實都要在內容裡標明來源與查證/發布日期，例如：「（來源：日本外務省官網，2026-08 查證）」

## Phase 1：依類型產出內容

用 `assets/templates/見聞錄-content.md` 或 `assets/templates/地方誌-content.md` 當骨架，把 `[內容]` 換成查證到的實際文字。**不要憑記憶重打骨架**——這兩份檔案是實際格式的唯一來源，段落標題、順序、來源標註格式都以檔案內容為準，這裡不重複貼一份容易跟檔案本身失去同步。

寫入前要用到 Notion 的 `<callout>`／`<columns>`／`<details>` 等排版語法時（例如頁面正文需要分欄呈現），先看 `references/notion-markdown-syntax.md`，裡面是已經驗證過能用的語法子集，不用每次都重新讀完整的 enhanced-markdown-spec。

## Phase 2：品質關卡

寫入前自我檢查：

- [ ] 每一項事實類資訊（地址/時間/價位/簽證規定）是否都標明了來源，或明確寫「未查證」？
- [ ] 簽證/法規類內容是否來自官方或高權威來源，且標了查證日期？
- [ ] 有沒有把「使用者原始描述」跟「查證到的資訊」混在一起、讓人分不清哪個是查證過的？
- [ ] 內容是否只是複製來源原文，還是有實際整理成使用者能一眼看懂的重點？
- [ ] 見聞錄：座標抓到了嗎？外部評分有沒有一起寫則數與擷取日？
- [ ] 見聞錄：評論是**歸納成三行共識**，還是只是貼了幾則評論？
- [ ] 餐廳：飲食適配三條都有指出依據嗎？查不到菜單有誠實填 `❓ 待確認菜單` 嗎？
- [ ] 非英語系國家：當地語言名稱填了嗎？語言功課的句子有中文近似音、唸得出來嗎？
- [ ] 自駕：ZTL／環保區／vignette 這類管制有查官方來源並標日期嗎？
- [ ] 票券：有沒有不小心下了「哪張最划算」的結論？（那是 route 的職責，這裡只列規則）

**沒有查到任何來源的 Quick Draft**：內容底部加一行 `> ⚠️ 內容待補強，目前只有使用者提供的資訊，未查證`，並在成熟度維持 `🌱 蒐集中/未去過`（不要因為寫了內容就誤調成 🌿）。

## Phase 3：整合與寫入 Notion

**核心原則跟 `knowledge-garden-page-content` 一致：更新是整合後的重寫，不是累加。** 但「✅ 親身驗證心得」是例外——那一區本來就設計成按日期累加（每趟旅程一段），不要整合覆蓋掉之前的心得。

1. 完整讀取現有頁面內容（不只看 Properties）
2. 「蒐集資料」區：新查證的資訊整合進去，推翻舊資訊時比照 knowledge-garden 的取代標記格式（`~~舊內容~~` + 修正說明），不要靜默覆蓋
3. 「親身驗證心得」區：不動，除非使用者明確要求修改自己寫過的心得
4. 更新「最後更新」欄位

### 發布前確認

- **簽證/法規類內容、或新建地方誌/見聞錄條目**：寫入前先在對話裡列出查證到的內容跟來源，等人類確認再寫入 Notion（跟 knowledge-garden-page-content 的 `[PREVIEW]` 規則一致）
- **既有見聞錄條目的小幅補充**（例如補一個營業時間）：不需要每次都預覽
- 批量處理多筆（例如一次幫一趟旅程的 5 間候選餐廳都查資料）時，用 `[BATCH_PREVIEW]` 格式列出每筆的來源摘要，取得確認後才寫入

## 注意事項

- **不要只讀 Properties 就產內容** — 必須先查證
- **簽證/法規類資訊沒有查到官方來源，就不要寫得斬釘截鐵** — 標「未查證」比寫錯安全
- **親身驗證心得不是本 skill 能代寫的東西** — 那是使用者真實經歷，本 skill 只負責蒐集資料區
- **不要覆寫使用者手動寫的心得** — 先讀取現有內容

## 何時改用其他 skill
- 要「建立/修改地方誌或見聞錄的屬性、關聯」→ `travel-map-knowledge-capture`
- 要「建立/修改旅程或行程項目」→ `travel-map-trip-planner`
- 要「旅程完成、整理心得分流寫回」→ `travel-map-trip-feedback`（心得本身不查證，只整理措辭）
- 只是要「查」資料 → `travel-map-query`
