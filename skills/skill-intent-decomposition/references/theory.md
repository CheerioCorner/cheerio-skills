# 這套拆法背後的理論

不是自己發明的野路子——「攤開事件、照動詞切」是軟體工程練了 20 年的老功夫，只是套到 2025 年才出現的 skill 系統上。

| 理論 | 定義 | 在 skill 拆分裡對應的做法 |
|---|---|---|
| **Event Storming**（事件風暴） | 把「發生的事」攤在時間軸上，從中找出邊界 | Step 1 收集人類意圖，就是把一句需求拆成好幾個具體事件 |
| **Bounded Context**（限界上下文） | 同一個詞，在不同情境是不同的東西，要各自割界 | 例：「工作」在查詢情境跟寫入情境是兩種模型（風險、副作用完全不同），要分開處理，不能共用一套邏輯 |
| **Single Responsibility**（單一職責） | 一支只做一件事；混在一起，注意力就會失焦 | 讀一支、寫一支，各司其職——一支 skill 的 description 如果要用「而且」才能講完，代表它可能還沒切乾淨 |
| **Design-First**（設計先行） | 先把邊界與契約想清楚，才動手寫程式 | 先畫決策樹，才決定切成幾支；不要邊寫 SKILL.md 邊猜邊界在哪 |

## 為什麼值得認這個祖宗

這幾個理論已經被驗證過幾十年，不是憑感覺切的。當有人問「這樣拆是不是太瑣碎/太隨意」，可以直接回到這張表：每一刀都有名字、有理由，不是隨手切的。

## 延伸：可攜性

這套拆法產出的是 skill 本身的**內容**（description + 流程 + references），不綁定特定 agent harness。GitHub Copilot 用 Agent/instructions/skills 組合、Claude 用 Skill API 或 project context、其他 agent harness 各有各的編排方式——但 skill 內容本身不用因為換平台而改寫，差異只在「誰負責串接呼叫」這一層。
