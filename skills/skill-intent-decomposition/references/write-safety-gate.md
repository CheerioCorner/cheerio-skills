# 寫入安全門（The Gate）

能跑，不代表該跑。Demo 成功之後，回頭確認「什麼」可以真的寫回去——這不只是某一個領域的規則，是**所有寫入類 skill 的安全邊界**，動手前判準要先立清楚。

## 判準

| 判準 | 說明 | 範例 |
|---|---|---|
| ✓ 要 | 明確的事實、明確的歸屬 | 「我的」升級案、指派給我的工作 |
| ✓ 要 | 可以被讀回驗證的狀態 | 已完成、已花 3 小時 |
| ⚠️ 小心 | 會動到別人的資料或正式設定 | 改到同事的工時 → 需要更高權限與授權 |
| ✕ 不要 | AI 推測、幻想、沒有證據的結論 | AI 自己猜出來的工時數字、憑印象寫的簽證規定 |

## 四步驟（沒有例外）

1. **`--dry-run`** — 先預覽，不動任何資料
2. **人類確認** — 把預覽結果攤給人看、等點頭
3. **`--confirm`** — 確認後才真正寫入
4. **讀回驗證** — 寫完再讀一次，核對無誤

不可逆的事，人類永遠先看過一眼。這條規則沒有例外——即使是「小幅補充」也建議至少讀回驗證，只有預覽確認這一步可以視風險高低省略（見下方分級）。

## 分級：不是每次都要重預覽

寫入風險不是均質的，判斷可以分級（可參考各領域 skill 的實際做法，例如 Cheerio 旅遊地圖的 `travel-map-page-content`／`travel-map-knowledge-capture`）：

- **高風險，必須預覽確認**：新建記錄、會影響其他人判斷的正式內容（例如簽證/法規類事實）、批量操作
- **低風險，可省略預覽**：單純的屬性更新（狀態、標籤）、既有記錄的小幅補充（補一個營業時間）

批量操作永遠不是例外——批量寫入前一律先輸出預覽清單（單筆用 `[PREVIEW]`、多筆用 `[BATCH_PREVIEW]`），列出每筆的關鍵內容，取得人類明確回覆確認後才寫入。

## 為什麼這麼堅持

寫入的成本是不對稱的：一次查詢錯了，重查一次就好；一次寫入錯了，可能覆蓋掉別人的資料、寫進錯誤的正式紀錄，事後很難完全復原。安全門的四步驟就是用最小的摩擦成本，換取寫入錯誤的機率趨近於零。
