# Skill Intent Decomposition

面對一個複雜領域，先決定「要拆成幾支 skill、邊界在哪」，再動手寫。**流程圖就是規格。**

## 何時改用其他 skill
- 邊界已經定案，要「寫 SKILL.md 初稿、測試觸發準確度、優化 description」→ `skill-creator`
- 只是要「修一支已存在的 skill 的小問題」（不涉及拆分）→ 直接編輯，不需要走這套流程
- 領域本身只有 2-3 條互不衝突的意圖 → 見下方「什麼時候不要拆」，可能根本不需要拆

## 核心原則

**地基不是流程圖，是 Domain Know-how。** 很多人以為畫決策樹是起點，其實決策樹只是把「人類先講清楚的意圖與領域脈絡」畫出來而已。地基不穩，上面的樹跟 skill 都會塌——所以第一步永遠是找人類（或既有對話/文件）把意圖收集齊，不是急著畫圖。

**為什麼不能塞成一支 mega-skill：**
- 意圖太多——一支要應付十幾種不同的事，觸發判斷會混亂
- 分支太深——多層結構、每層各有規則，讀起來像迷宮
- 寫入風險不一——查詢跟寫入的安全要求天差地遠，混在一起容易「順手」做了不該做的事

## 流程

### Step 1：收集人類意圖（地基）

跟人類訪談（或從既有對話/文件提取），列出「人類會對這個領域做的所有事」，每條用一句自然語言短句寫下來，不是規格文件。同時標記這條意圖：
- 跟哪個**資源/層級**有關？（例如 travel-map 案例裡的「地方誌」vs「旅程」）
- 是**讀**還是**寫**？寫的話，寫錯的後果有多嚴重？
- 觸發時機是「隨時」還是「特定事件之後」？（例如「旅程完成後」這種時機獨立的意圖，很適合自己切一支）

意圖列得不夠齊，後面切出來的邊界一定會漏東西——這一步值得花時間，不要跳過直接猜。

### Step 2：畫決策樹，找葉節點

把收集到的意圖畫成一棵決策樹：
1. 先按「同一個詞在不同情境是不同東西嗎？」（Bounded Context）分大枝——通常是資源層級或知識/操作的分野
2. 同一枝底下如果意圖夠多、夠雜，再照**動詞**細分：查詢（唯讀）／維護（新增與更新）／呈現（彙整給人看）／分析（依規則整理報表）——這組動詞不是唯一解，依領域實際需要的動作決定
3. 找出**跨枝的共用關切**（認證、內容查證、某個橫跨多資源的特殊工作流程），獨立拉成自己的一支，不要塞進任何一個資源分枝裡
4. **每個葉節點 = 一支 skill 的邊界**

判斷「這樣拆對不對」的準則：
- 拆的理由必須是真實的邊界（Bounded Context、寫入風險不同、觸發時機不同），不是為了拆而拆
- 一支 skill 應該只做一件事（Single Responsibility）；如果你在描述一支 skill 時一直用「而且」，它可能還要再拆

### Step 3：收斂成 N 支 skill 規格

每個葉節點產出：
- **name**：跟資源/動詞相關的簡短名稱
- **description 草稿**：不只寫「這支做什麼」，還要寫「什麼情況下不要用這支、改用哪支」——讓 description 本身就是決策樹的一個節點，觸發判斷才會準
- **邊界一句話**：這支唯一負責的事是什麼

把這份清單交給人類確認，確認後**逐支**交給 `skill-creator` 走草稿→測試→優化的流程。不要自己在這裡土法煉刻寫 SKILL.md 全文再回頭調整——那是 skill-creator 的職責。

## 撰寫技巧：明確給資產，模糊留彈性

最佳區域在「核心明確、細節按需載入」，不是兩個極端：
- 過度明確（全部寫死、大量 if/else）→ 換個情境就壞掉，維護成本隨規則爆增
- 過度彈性（什麼都不規定）→ 每次理解都不一樣，很難測試

具體做法：SKILL.md 放**原則與決策點**；`scripts/` 放**可執行的重複動作**；`references/` 放**細節與領域知識**；`assets/` 放**範本與資源**；情境判斷留給 AI，不要用 if/else 窮舉。這正是「本 skill 為什麼要拆成 SKILL.md + references/」的自我示範——見下方。

## 寫入類 skill 的安全門（不只本流程適用）

任何葉節點只要涉及「寫入」，都要過這道門，沒有例外：
1. **--dry-run**：先預覽，不動任何資料
2. **人類確認**：把預覽結果攤給人看、等點頭
3. **--confirm**：確認後才真正寫入
4. **讀回驗證**：寫完再讀一次，核對無誤

判準：明確的事實、明確的歸屬、可以被讀回驗證的狀態 → 可以寫。會動到別人的資料或正式設定 → 小心，可能需要更高權限。AI 推測、幻想、沒有證據的結論 → 不要寫。完整細節見 `references/write-safety-gate.md`。

## Skill 組合技

複雜情境不是一支 skill 打完，是**串接**多支：例如「查詢 → 讀領域知識 → 分析比對 → 確認後寫入」這樣的鏈。切得細，正是為了能照情境組合，不是為了數量好看。這也是為什麼 Step 2 找到的葉節點要各自獨立、可重用，而不是互相依賴內部細節。

## 什麼時候不要拆這麼細

如果意圖只有 2-3 條、彼此語意不衝突、不會被同時觸發搞混，拆成多支反而是過度工程——單一 skill 內用清楚的段落區分即可。回頭看 Step 1 收集到的意圖數量與衝突程度再決定，不要看到「有多個資源」就反射性地拆。
