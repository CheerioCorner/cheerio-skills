# Travel Map Knowledge Capture

新增/維護地方誌、見聞錄的記錄與屬性關聯。**唯一負責寫入這兩個資料庫屬性的 skill。**

## 何時改用其他 skill
- 一次只有一筆、資訊完整（知道地方也知道類別）→ 不用進 Inbox 模式，直接走流程 1/2 就好，Inbox 是給「一次很多筆、當下沒空一個個確認」的情境
- 只是要「查」地方誌/見聞錄 → `travel-map-query`
- 要「排進某趟旅程」→ `travel-map-trip-planner`
- 要「幫這筆記錄查證/寫正文內容」→ `travel-map-page-content`（本 skill 建好屬性後應該接著呼叫它）
- 要「旅程完成、整理心得」→ `travel-map-trip-feedback`

## 開工前必讀

`travel-map-query/schemas/travel_map_schema.yaml`（另一個 skill 目錄下）—— data source ID、屬性名稱、選項清單都在這裡。

## 流程

### 1. 新增地方誌條目（新目的地）
1. 先用 `travel-map-query` 確認是否已存在同名條目，避免重複
2. 決定分類（國內/國外）、洲（國外才填）、國家、城市或區域（選填，只在需要細分時才填）
3. 建立 Database 記錄，成熟度預設 `🌱 蒐集中/未去過`
4. 呼叫 `travel-map-page-content` 補上頁面內容
5. 不要自己建立「關聯旅程」「關聯見聞錄」——這兩個是反查欄位，等旅程/見聞錄那邊建立關聯後自動出現

### 2. 新增見聞錄條目（餐廳/景點/住宿/店家/主題筆記）
1. 先確認對應的地方誌條目存在，不存在就先做流程 1
2. 建立見聞錄記錄，「所屬地方誌」關聯到那一頁，「類別」選對應選項
3. 「細部地點」只在地方誌那層還不夠細時才填（例如所屬地方誌=大阪，細部地點=心齋橋）
4. 成熟度預設 `🌱 蒐集中/未去過`
5. 呼叫 `travel-map-page-content` 補上頁面內容

> 判斷準則：**這是不是一個地方本身（有座標、可以被造訪）？** 是 → 見聞錄；不是（簽證/習俗/交通通則這類「關於地方的知識」）→ 寫進地方誌那一頁的正文，不要為它單獨開見聞錄頁。

### 3. Inbox 模式（批次收集，貼上就走）

**設計目的**：Cheer 平常收集景點的方式是刷影片/滑貼文時當下丟進來，一次可能三五個，且當下未必知道城市層級。這個流程的唯一目標是**把摩擦壓到最低**——貼上就存，不要因為要先想清楚分類就讓人懶得存。

**觸發情境**：使用者一次給多個連結（IG/YouTube/小紅書/部落格/Google Maps 分享連結）、多張截圖，或說「這幾個都存起來」「先丟進來」「剛滑到的都幫我存」。

**流程**：

1. 逐項判斷這筆的所屬地方誌與類別能不能當下確定：
   - **能確定**（連結內容、使用者附帶文字、截圖上的地名/語言看得出城市或國家）→ 走流程 1/2 正常建立，`收集狀態` = `✅ 已整理`
   - **不確定** → `所屬地方誌` 先關聯到固定佔位條目 **「📥 待分類（Inbox 佔位）」**（地方誌資料庫裡已經有這一筆，不要自己重建），`類別` 用最寬的猜測（不確定就填 `📚 主題筆記`），`收集狀態` = `📥 待分類`
2. **每一筆直接建立，不要逐筆詢問確認。** 批次結束後一次跟使用者回報這次收了幾筆、幾筆已歸位、幾筆待分類，讓他掃一眼就好
3. 座標／來源連結**只做零成本擷取，不做查證**：
   - Google Maps 分享連結網址裡通常有 `@緯度,經度`，能解析就直接填入 `座標`
   - 其他連結一律填 `來源連結`，`座標` 留空即可，不要為了填座標特地開 WebFetch 深爬——那是 `travel-map-page-content` 的工作
4. 批次收集完成後，把這批裡 `收集狀態` = `✅ 已整理` 的項目交給 `travel-map-page-content` 用 Quick Draft 模式補內容，走它既有的 `[BATCH_PREVIEW]` 流程一次列出來源摘要讓使用者確認——**查證是那一步的事，Inbox 本身不查證**
5. `📥 待分類` 的項目**不要**自動送進 `travel-map-page-content`——地方誌都還沒確定，查了也是白查。等使用者自己說「這幾個是京都的」之類的話，才一次性把 `所屬地方誌` 改過去、`收集狀態` 改回 `✅ 已整理`，再送查證

**回顧待分類清單**：使用者問「還有哪些待分類」「Inbox 清一下」時，用 `travel-map-query` 查 `所屬地方誌` = 「📥 待分類（Inbox 佔位）」的見聞錄，列出來讓使用者一次歸位。

## 本 skill 負責的屬性（v1.2 起有明確分工）

| 這裡寫 | 交給 `travel-map-page-content` 回填 |
|--------|-----------------------------------|
| 條目名稱、分類、洲、國家、城市或區域、貨幣、主要語言、英文通用度 | — |
| 類別、所屬地方誌、細部地點、收集狀態 | 座標、當地語言名稱、外部評分、評論數、評價查證日、建議停留、飲食適配、子類別、來源連結、AI 摘要、最後更新 |

`成熟度` 一律建為 `🌱 蒐集中/未去過`；`喜愛度` 這裡不填（由 `travel-map-trip-feedback` 在去過之後寫）。

## 規則
- 建好屬性/關聯後，內容一律委派 `travel-map-page-content`，不要自己在這裡憑印象寫查證過的事實（尤其簽證/法規類）
- 新建前先查重複；不確定就用 `travel-map-query` 查一次
- 不要自己填座標、評分、飲食適配這類「查證才知道」的欄位——那是 page-content 的產物，這裡憑印象填會失真
- Inbox 批次收集時**不要逐筆反問使用者**，這違背這個模式存在的目的；真的完全看不出任何線索（連當地語言名稱、圖片內容都判斷不出來）才整批問一次，不要一筆一筆問
